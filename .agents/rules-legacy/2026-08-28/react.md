# React 开发规则

## 适用范围

本规则适用于 `web/src` 下所有 React 组件、Hooks、路由模块、Provider、浏览器端
状态和异步交互。当前项目以 Vite、React 和 React Router 为基础，不套用
Next.js、React Server Components 或 Server Actions 专属模式。

## 设计原则与优先级

1. 先保证状态正确、职责清晰和可维护性，再根据真实构建产物与运行表现进行优化。
2. 优先消除请求瀑布和无关的大型依赖，其次减少无效渲染，最后才考虑循环、缓存等
   微优化。
3. 复用 React、React Router、shadcn 和现有依赖提供的标准能力，不重复实现已有
   原语，不为尚未出现的需求建立抽象或兼容层。
4. 所有项目内部导入同时遵守 `.agents/rules/imports.md`，统一使用 `@/`。

## 模块与路由边界

1. 路由实例、应用级配置和必须只执行一次的初始化放在 React 树外创建，不放在
   组件的 `useEffect([])` 中重复初始化。
2. 按业务功能划分路由加载边界。聊天、图表、编辑器、代码高亮等大型功能必须在
   对应功能路由或布局内按需加载，不能因为全局入口或根 Provider 让无关页面承担
   其依赖成本。
3. 全局 Provider 只放所有页面都需要的基础能力。业务 Provider 应靠近其使用的
   路由边界，相关全局样式也应随业务模块加载。
4. 懒加载以功能或路由为粒度，不把每个轻量组件拆成独立 chunk。可以根据明确的
   下一步操作在悬停、聚焦等用户意图出现时预加载对应模块。
5. `index.ts` 只作为模块对外公共入口。模块内部导入具体实现文件，不经由本模块
   的公共 barrel 回流，避免循环依赖和不必要的模块加载。
6. 动态导入路径必须能够被构建工具静态分析；禁止通过任意字符串拼接模块路径。

## 异步与数据请求

1. 相互独立的异步任务同时启动，并通过 `Promise.all` 等待；只有存在真实数据依赖
   时才串行执行。
2. 在确定某个分支确实需要结果后再 `await`，不要让提前等待阻塞无需该数据的路径。
3. 用户点击、提交、拖放等操作引发的请求直接放在对应事件处理函数或业务 Hook
   中，不使用“设置状态，再由 effect 监听状态”间接触发。
4. 页面级数据优先在路由数据边界或明确的数据 Hook 中组织；禁止在多个组件中对
   同一资源各自编写重复请求。
5. 搜索、切换页面等可能产生竞态的请求必须具备取消、失效或只接受最新结果的
   机制。加载、失败、空数据和重试状态必须显式建模。
6. 不因为规范示例提前引入 SWR 或其他请求库；当真实业务出现共享缓存、请求去重
   或重验证需求时再统一选型。

## State、Effect 与 Hooks

1. 能由当前 props、state 或路由参数计算出的值，在渲染期间直接派生，不另存一份
   state，也不使用 effect 同步。
2. 根据旧 state 计算新 state 时使用函数式更新，例如
   `setItems(current => [...current, item])`，避免陈旧闭包。
3. 昂贵的初始计算、本地存储解析和索引构建使用惰性初始化
   `useState(() => initialValue)`；简单字面量不需要包装。
4. Effect 只负责与 React 外部系统同步。依赖项应完整且尽量使用真正相关的原始值，
   禁止通过遗漏依赖、关闭规则或无意义的 ref 掩盖问题。
5. 频繁变化但不参与渲染的临时值使用 `useRef`；会改变界面的值使用 state。
6. 大型搜索结果、图表或其他已经产生输入卡顿的派生渲染，可以使用
   `useDeferredValue` 或 transition；普通表单不得无条件增加这些复杂度。
7. 自定义 Hook 必须表达可复用的状态或副作用边界。仅包装一次简单函数、常量或
   JSX 的逻辑不创建 Hook。

## 组件与渲染

1. 不在组件函数内部声明新的 React 组件。需要拆分时提升到模块作用域，并通过
   props 传递数据，避免每次渲染产生新的组件类型和重新挂载。
2. 组件保持单一职责，但不把只使用一次的少量 JSX 机械拆成文件。抽取的依据是
   复用、独立状态、副作用边界、可测试性或明显的复杂度，而不是代码行数。
3. 不为简单字符串、数字、布尔计算使用 `useMemo`，不为普通事件处理器机械添加
   `useCallback`，不在没有测量依据时全面使用 `memo`。
4. Props 和 state 视为只读。排序使用 `toSorted()` 或复制后排序，禁止直接调用
   `sort()`、`reverse()` 等可变方法修改来源数据。
5. 当条件可能是数字、`NaN` 或空字符串时使用显式判断与三元表达式，避免
   `value && <Component />` 意外渲染 `0` 等值。
6. 列表必须使用稳定的业务标识作为 key。禁止在可增删、排序或过滤的列表中使用
   数组下标或运行时随机值。
7. 长消息列表等真实出现渲染压力后，优先评估现有组件能力、`content-visibility`
   或虚拟列表；不提前维护自制虚拟化方案。

## 依赖与构建性能

1. 新增大型依赖前检查现有依赖是否已经提供相同能力，并检查其 ESM、Tree Shaking
   和按需加载方式。
2. 不在应用入口静态导入只有少数路由需要的编辑器、Markdown、语法高亮、数学、
   图表、地图或媒体处理依赖。
3. 第三方包优先采用其官方支持的导入方式。不要为了规避 barrel import 擅自使用
   未公开的深层路径；是否调整必须通过类型检查和构建产物验证。
4. 非关键的统计、日志和预加载不得阻塞首屏或用户正在等待的操作；确有需要时再用
   idle 调度，并为必须完成的任务设置明确时限。
5. 性能修改必须有构建大小、Profiler、浏览器性能记录或可复现卡顿作为依据，不能
   只凭代码看起来更“优化”。

## 浏览器状态与事件

1. `localStorage`、`sessionStorage` 和 Cookie 只保存界面确实需要的最小数据，读写
   必须处理不可用、隐私模式和容量异常；禁止保存令牌、密码或不必要的完整用户对象。
2. 不为尚不存在的迁移需求预先设计 `v1`、`v2` 配置分支或兼容读取逻辑。结构真正
   发生变化时，根据当时的数据和发布策略处理。
3. `touch`、`wheel` 等不会调用 `preventDefault()` 的监听器使用 passive 模式。
4. 多个组件需要相同的全局事件时，共享订阅或由上层统一注册，避免重复添加同类
   window/document 监听器。
5. DOM 测量先集中读取，再集中写入；优先切换 CSS 类，避免读写交错导致强制布局。

## 禁止事项

- 禁止把 Next.js、RSC 或 Server Action 的规则直接套用到当前 Vite 客户端项目。
- 禁止以性能为名复制第三方组件实现、创建无需求的兜底层或增加预防性抽象。
- 禁止使用 effect 维护可派生状态、代替用户事件或执行应用级重复初始化。
- 禁止为了减少渲染而破坏状态正确性、依赖完整性、可访问性或国际化。
- 禁止在没有分析构建产物或运行性能前进行大规模 memo 化和微优化。

## 验收清单

- `npm run format`
- `npm run lint`
- `npm run typecheck`
- `npm run build`
- 检查新增路由是否只加载所属功能依赖，首屏没有被无关大型模块污染。
- 检查异步流程不存在可避免的串行等待、重复请求或竞态覆盖。
- 检查没有新增派生 state、事件驱动 effect、组件内组件或 props/state 原地修改。
- 涉及性能优化时，记录优化前后的构建大小或运行测量结果。
