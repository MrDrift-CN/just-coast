# 国际化开发规则

## 适用范围

本规则适用于 `web/src` 下所有面向用户的页面、业务组件、共享组件、提示信息、
可访问性文案和数据格式化逻辑，不局限于认证或任何单一业务模块。

## 唯一事实来源

- 国际化基础设施统一由 `web/src/i18n` 管理。
- 翻译资源统一存放在
  `web/src/i18n/resources/<BCP-47 locale>/<namespace>.json`。
- 支持语言、默认语言和语言偏好统一由 `locale.ts` 定义。
- 初始化配置和 namespace 聚合统一由 `config.ts` 管理。
- 语言切换统一通过 `useLocale()`；可复用入口使用 `I18nButton`。

## 必须遵守

1. 所有面向用户的固定文案必须来自翻译资源，包括标题、正文、按钮、菜单、
   表单标签、占位符、校验提示、空状态、Toast、Tooltip、`aria-label` 和
   `title`。
2. React 组件使用 `useTranslation(namespace)`；非 React 模块确实需要翻译时
   才使用项目导出的 `i18n.t()`。
3. namespace 按业务域拆分；`common` 只保存跨业务域复用的文案，不按单个页面
   创建 namespace，也不把所有文案集中到 `common`。
4. 翻译键使用稳定、语义化的嵌套结构。界面文案变化时不应迫使业务代码更换键。
5. 每种受支持语言必须保持相同的键结构；新增、修改或删除翻译键时同步维护全部
   语言资源。
6. 语言代码必须使用 BCP 47 标签，例如 `zh-CN`、`en-US`。
7. 动态内容使用插值、复数和上下文能力，不通过字符串拼接组织句子。
8. 日期、时间、数字、货币、百分比、列表和相对时间使用 i18next/Intl 格式化，
   不手写与语言区域相关的格式。
9. 后端错误必须通过稳定错误码映射到翻译键；不得直接向用户展示内部异常文本。
10. 新增语言时，必须同步更新语言类型、资源注册、语言显示名称和类型声明，并在
    真实界面中检查布局。

品牌名称、协议标识、用户生成内容和后端返回的业务数据不作为固定界面文案翻译；
其周围的说明性文案仍必须国际化。

## 禁止事项

- 禁止在 JSX、TSX、JS、TS 或样式伪元素中新增可见的硬编码界面文案。
- 禁止在组件中直接操作 i18next 语言状态、语言本地存储键或浏览器语言检测器。
- 禁止为相同含义创建多个近似翻译键，也禁止跨业务域读取不属于当前模块的
  namespace。
- 禁止依赖 fallback 掩盖缺失翻译；受支持语言的资源必须完整。
- 禁止为了适配某一种语言写死组件尺寸；稳定控件应预留明确尺寸，内容区域应允许
  合理伸缩，并验证长文案不会溢出或意外换行。

## 扩展流程

### 新增业务文案

1. 确定现有业务 namespace；只有形成新的业务域时才新增 namespace。
2. 在全部语言的同名资源文件中添加相同键。
3. 在组件边界调用 `useTranslation(namespace)` 并使用 `t()`。
4. 同时检查可见文案、可访问性文案和错误状态。

### 新增语言

1. 在 `locale.ts` 注册 BCP 47 语言代码和显示信息。
2. 为每个现有 namespace 创建完整资源文件。
3. 在 `config.ts` 注册资源，并同步 `i18next.d.ts` 类型来源。
4. 使用语言选择组件验证切换、持久化、系统语言和文档 `lang`/`dir`。

## 验收清单

- `npm run typecheck`
- `npm run lint`
- `npm run build`
- 至少使用 `zh-CN` 与 `en-US` 检查主要状态和响应式布局。
- 检查缺失键、插值、复数、日期/数字格式、长文案、键盘操作和屏幕阅读器名称。
