# Git / Commit 规范

## 分支

- 禁止直接向主分支提交或推送功能变更。
- 每个分支只解决一个可以独立说明和验证的目标。
- 分支名使用 `<type>/<short-description>`，描述部分使用小写短横线。
- 允许的常用类型包括 `feat`、`fix`、`refactor`、`docs`、`test`、`chore`。
- 分支存续时间应尽量短，及时同步主分支，降低合并冲突。
- 禁止在共享分支上执行会破坏他人历史的强制推送；确需重写个人分支历史时必须确认没有其他协作者依赖。

## 提交消息

提交标题格式为：

```text
<type>[optional scope][optional !]: <description>
```

允许的类型：

| 类型       | 用途                             |
| ---------- | -------------------------------- |
| `feat`     | 新功能或新的用户能力             |
| `fix`      | 缺陷修复                         |
| `docs`     | 仅文档变更                       |
| `style`    | 不影响行为的格式或样式整理       |
| `refactor` | 不新增功能、不修复缺陷的结构调整 |
| `perf`     | 可说明收益的性能优化             |
| `test`     | 测试新增或调整                   |
| `build`    | 构建系统、依赖或打包配置         |
| `ci`       | 持续集成和自动化流程             |
| `chore`    | 其他不影响产品行为的维护工作     |
| `revert`   | 回退已有提交                     |

## 标题要求

- `type` 和 `scope` 使用小写英文。
- `scope` 可选，必须描述稳定模块，例如 `auth`、`i18n`、`theme`、`ui`、`deps`。
- 冒号后必须有一个空格。
- 描述应简洁说明本次变更做了什么，不写模糊的 `update`、`changes`、`fix issue`。
- 描述使用祈使语义，不以句号结尾。
- 标题长度不超过 100 个字符。
- 一个提交同时满足多个类型时，应优先拆为多个独立提交。

## 正文和脚注

- 简单变更可以省略正文。
- 需要说明动机、取舍、迁移方式或测试限制时必须写正文。
- 正文与标题之间保留一个空行。
- 脚注与正文之间保留一个空行。
- 破坏性变更必须使用标题中的 `!` 或 `BREAKING CHANGE: <description>` 脚注明确标记。
- 关联任务、审阅信息和回退目标放在脚注，不塞入标题。

## 提交内容

- 一个提交表示一个逻辑完整且仓库仍可正常工作的变更。
- 功能修改应包含对应测试或明确的现有验证。
- 大规模重构、文件移动和格式化应与功能修改分开提交。
- 不提交调试日志、临时文件、编辑器缓存、构建产物和本地环境配置。
- 锁文件只在依赖或包管理解析结果确实变化时提交。
- 禁止提交密钥、令牌、密码、真实个人数据和包含敏感值的环境文件。

## Pull Request

- PR 应保持小而自洽，完成一个明确目标，并能独立构建和验证。
- 不设置机械行数上限；当评审者难以一次理解设计和风险时必须拆分。
- 重构与功能变更原则上分开，必要的小范围清理可以随功能提交。
- PR 描述至少说明目的、主要变化、验证结果、风险和必要的迁移步骤。
- UI 变更应提供能够说明结果的截图或录屏。
- 生成代码或上游组件发生修改时必须明确指出修改范围和原因。
- 所有必需 CI 检查通过后才能合并。

## 合并与回退

- 合并前确认提交标题符合规范，尤其是 squash 合并产生的最终标题。
- 不能为了通过检查修改或跳过与变更无关的失败；应先确认失败归属。
- 回退使用独立 `revert` 提交并说明目标提交和原因。
- 紧急修复仍必须保持最小范围、可验证和可回退，后续补充遗漏的测试与文档。

## 项目案例

以下案例覆盖本文件全部规则章节。命令仅说明预期结果，不要求在当前任务中执行提交或推送。

### 案例：短生命周期单目标分支

**覆盖**：禁止主分支直提、单一目标、分支格式、允许类型、及时同步、强推边界。

```text
❌ master
❌ feature/Login_New_And_Theme
❌ feat/everything

✅ feat/account-settings
✅ fix/auth-expired-session
✅ refactor/theme-storage
```

登录修复和主题重构应使用不同分支。个人分支只有确认无人依赖时才可安全重写；共享分支不得强推覆盖他人历史。

### 案例：有效和无效的提交标题

**覆盖**：格式、类型、scope、空格、准确描述、祈使语义、句号、长度、拆分类型。

```text
❌ Update files
❌ feat(Auth): added login.
❌ fix: fix issue
❌ feat: add login and refactor theme and format project

✅ feat(auth): add password visibility control
✅ fix(i18n): preserve locale during legacy-key migration
✅ refactor(theme): centralize preference parsing
✅ docs(rules): add project examples
```

`type` 和稳定 `scope` 使用小写；冒号后一个空格，描述不以句号结尾并控制在 100 字符内。功能、重构和全仓格式化应拆分。

### 案例：选择正确提交类型

**覆盖**：全部允许类型及其职责边界。

| 变更               | 类型示例      |
| ------------------ | ------------- |
| 新增语言切换能力   | `feat(i18n)`  |
| 修复过期响应覆盖   | `fix(api)`    |
| 只改规范文字       | `docs(rules)` |
| 只做无行为格式整理 | `style`       |
| 保持行为的目录重构 | `refactor`    |
| 经测量减少首包     | `perf`        |
| 增加迁移测试       | `test`        |
| 修改 Vite/依赖构建 | `build`       |
| 修改 CI 工作流     | `ci`          |
| 其他维护工作       | `chore`       |
| 回退已合并提交     | `revert`      |

### 案例：正文、脚注与破坏性变更

**覆盖**：可省略正文、动机与迁移、空行、脚注、`!`/`BREAKING CHANGE`、任务与回退信息位置。

```text
feat(theme)!: rename persisted preference schema

Read preferences.theme first and migrate the legacy key after a valid write.

BREAKING CHANGE: custom theme adapters must provide schemaVersion.
Refs: JC-218
```

简单文档错字可以只有标题。复杂迁移需要正文解释原因和验证；任务编号不应挤进标题。

### 案例：一个提交保持仓库可工作

**覆盖**：逻辑完整、测试/验证、重构和格式分离、禁止临时产物、锁文件、敏感数据。

- ✅ API 字段迁移提交同时包含类型、适配器、调用方和测试，提交后仍可构建。
- ❌ 先提交只改类型、下一提交才修复全部编译错误。
- ❌ 功能提交夹带调试日志、编辑器目录、`dist` 和真实 `.env`。
- ✅ 只有依赖解析变化时提交锁文件；敏感令牌、密码、真实个人数据绝不进入历史。

### 案例：可评审的 Pull Request

**覆盖**：小而自洽、以理解成本拆分、重构边界、描述内容、UI 证据、上游说明、CI。

```text
目的：修复语言偏好旧键迁移后丢失的问题
主要变化：新键优先读取；合法旧值一次性写入 preferences.language
验证：lint、typecheck、迁移单元测试、两种语言人工切换
风险：localStorage 不可用时回退默认语言
迁移：成功写新键后删除旧键
```

UI 变化附亮/暗、窄屏和长文案截图。修改官方组件时明确文件和原因。评审者无法一次理解风险时拆分，不用机械行数上限；必需 CI 未通过不能合并。

### 案例：合并失败归属与安全回退

**覆盖**：squash 标题、无关失败、独立 revert、紧急修复后续工作。

- squash 前把最终标题改为合规的 `fix(auth): prevent duplicate login submission`。
- CI 失败先判断是否由本变更导致；不能直接跳过检查，也不在当前 PR 擅自修复完全无关的大问题。
- 回退使用 `revert(auth): revert session refresh change`，正文标明目标提交和原因。
- 紧急修复保持最小、可验证、可回退；来不及完成的测试和文档必须形成明确后续项。
