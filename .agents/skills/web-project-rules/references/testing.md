# 测试规范

## 适用范围

适用于 `web` 的静态检查、单元测试、组件测试、集成测试、端到端测试和人工验证。

## 当前最低门禁

在正式测试框架尚未纳入项目之前，每个代码变更至少必须通过：

- Prettier 检查。
- ESLint 检查。
- TypeScript 类型检查。
- 生产构建。
- 与变更范围相匹配的人工功能验证。

不得把“当前没有测试框架”解释为无需验证。高风险纯逻辑应优先设计为可测试的纯函数；如果没有可靠的人工方式覆盖，应在独立变更中先引入合适测试能力。

## 引入测试框架

- 测试框架必须与当前 Vite、React 和 TypeScript 主版本兼容。
- 引入变更应独立完成配置、示例、脚本和 CI，避免与大功能混在一起。
- 默认优先选择与 Vite 集成良好的单元测试环境和面向用户行为的 React 组件测试方式。
- 端到端工具只在关键跨页面流程确实需要浏览器级验证时引入。
- 不同时引入功能重叠的多套测试框架。

## 测试分层

- **静态检查**：发现格式、语义、类型和构建问题。
- **单元测试**：验证纯函数、解析、状态转换和错误映射。
- **组件测试**：验证用户可观察的渲染和交互。
- **集成测试**：验证多个模块、请求适配器和状态之间的协作。
- **端到端测试**：验证少量关键用户旅程和真实浏览器行为。

尽可能使用成本最低但能够覆盖风险的层级，不能用大量端到端测试替代可快速定位问题的低层测试。

## 必须覆盖的变化

测试能力到位后，以下变更必须新增或更新测试：

- 缺陷修复，至少包含能够复现原问题的用例。
- 解析、格式化、权限、校验和状态转换逻辑。
- API 错误、取消、超时和过期响应处理。
- 持久化结构和迁移逻辑。
- 具有条件分支的自定义 Hook。
- 关键表单、认证和不可逆操作。
- 影响国际化、主题或可访问性的重要共享组件。

纯文案、工具生成且未经修改的上游代码或仅由格式化产生的变化可以不新增测试，但仍必须通过相关静态检查。

## 测试设计

- 测试行为和公开契约，不绑定组件内部 State、私有函数或 DOM 实现细节。
- 组件测试优先按角色、可访问名称和用户可见文本查询元素。
- 每个测试只表达一个清晰场景，但可以包含完成该场景所需的连续用户步骤。
- 测试名称说明前置条件、动作和预期结果。
- 准备、执行和断言应结构清晰。
- 失败消息应能帮助定位行为，不依赖大面积快照比对。

## 测试数据与替身

- 测试数据最小化，只包含场景需要的字段。
- 不使用真实密码、令牌、用户信息和生产地址。
- 时间、随机数、网络和浏览器 API 必须可控。
- Mock 只替换真正的外部边界，不把被测模块内部全部 Mock 掉。
- API 测试替身应保留真实协议的重要状态码、延迟、取消和错误形态。
- 每个测试必须独立，不能依赖执行顺序或前一个测试遗留状态。

## 异步测试

- 等待用户可观察的结果，不使用任意 sleep 规避竞态。
- 必须断言加载、成功和错误中的实际相关状态。
- 对防抖、计时器和超时使用可控时钟，并在测试后恢复。
- 请求竞态测试必须验证过期结果不会覆盖最新结果。
- 取消操作不应产生未处理 Promise 或错误日志。

## 快照与覆盖率

- 快照只适用于结构稳定且人工审阅差异有价值的小范围输出。
- 禁止用大型组件快照代替行为断言。
- 覆盖率用于发现风险盲区，不以追求数字为目标添加无意义断言。
- 高风险逻辑即使总体覆盖率较高也必须有针对性用例。

## 测试维护

- 生产行为变化时同步修改测试，不允许长期跳过或注释失败测试。
- 不稳定测试必须修复根因；临时隔离时要记录原因和恢复条件。
- 测试代码同样遵守可读性、类型和复杂度规范。
- 删除功能时同步删除失效测试和测试数据。

## 项目案例

以下案例覆盖本文件全部规则章节，并反映项目当前尚未配置正式测试脚本的事实；案例中的测试 API 只有在测试框架独立接入后才可使用。

### 案例：没有测试框架也必须验证

**覆盖**：Prettier、ESLint、类型、生产构建、人工验证，以及高风险逻辑的可测试设计。

修改语言切换时的最低记录示例：

```text
通过：Prettier changed-files、npm run lint、npm run typecheck、npm run build
人工：zh-CN -> en-US -> 刷新仍保持；localStorage 禁用时回退 zh-CN
浏览器：控制台无新错误，document.lang 同步更新
```

不能写“项目没有 Vitest，所以未验证”。复杂迁移逻辑应先做成纯函数；人工无法可靠覆盖时，用独立变更引入测试能力。

### 案例：独立引入匹配项目的测试框架

**覆盖**：版本兼容、独立配置/示例/脚本/CI、Vite 集成与用户行为、E2E 适用条件、禁止重复框架。

- ✅ 单独 PR 核对 Vite 8、React 19、TypeScript 6，加入一个纯函数测试和一个按角色交互的组件测试，并接入脚本与 CI。
- ❌ 在大型认证功能 PR 中顺手同时引入两套单元测试框架和两个 E2E 工具。
- ✅ 只有登录、注销、关键数据提交等跨页面真实浏览器流程需要时再引入 E2E。

### 案例：选择成本最低的测试层级

**覆盖**：静态、单元、组件、集成、E2E 分工和测试金字塔。

| 风险                     | 合适层级            |
| ------------------------ | ------------------- |
| Locale 解析与旧键迁移    | 单元测试            |
| 登录按钮禁用和错误提示   | 组件测试            |
| 请求适配器与会话状态协作 | 集成测试            |
| 用户从登录到进入受保护页 | 少量 E2E            |
| 类型或非法导入           | TypeScript / ESLint |

不要用完整浏览器 E2E 验证每个纯函数分支，也不要认为类型检查能验证真实交互。

### 案例：哪些变化必须补测试

**覆盖**：缺陷、解析/权限/校验/转换、API 边界、持久化、Hook、关键流程、i18n/主题/a11y，以及可豁免变化。

- 修复“旧响应覆盖新搜索”：先写能稳定复现竞态的失败测试。
- 修改 `preferences.language` 结构：测试有效值、损坏值、旧键迁移和写入失败。
- 修改 `useLogin` 条件分支：测试重复提交、取消、认证错误和恢复。
- 修改共享 Dialog：测试焦点进入、Escape、焦点返回和翻译名称。
- 仅修正开发注释或未经修改的官方生成文件可不新增测试，但仍运行相关静态门禁。

### 案例：测试公开行为而非内部实现

**覆盖**：公开契约、可访问查询、单场景、测试名称、结构和失败可诊断性。

```tsx
it("disables submit while login is pending and prevents a second request", async () => {
  renderWithLocale(<FormLogin />, "en-US");

  await user.type(
    screen.getByRole("textbox", { name: /email/i }),
    "user@example.test",
  );
  await user.click(screen.getByRole("button", { name: /sign in/i }));

  expect(screen.getByRole("button", { name: /sign in/i })).toBeDisabled();
  expect(loginRequest).toHaveBeenCalledTimes(1);
});
```

不要读取组件私有 State、调用私有函数或查询脆弱 CSS 层级。连续输入和点击属于同一个用户场景，可以在一个测试中表达。

### 案例：最小数据和真实边界替身

**覆盖**：最小测试数据、无真实敏感值、可控时间/随机/网络/API、Mock 外部边界、协议形态、测试隔离。

```ts
const accountDto = {
  id: "account-1",
  display_name: "Demo User",
  created_at: "2026-08-28T00:00:00Z",
};
```

测试地址使用保留测试域或本地替身，不用生产地址、真实 token 和真实用户。Mock 传输层返回真实状态码、延迟与错误结构，不把 `authAdapter` 等被测内部实现全部 Mock。每个测试重置存储、计时器和替身，不能依赖执行顺序。

### 案例：等待行为而不是睡眠

**覆盖**：可观察结果、状态断言、可控时钟、竞态、取消无未处理错误。

- ❌ `await sleep(1000)` 后假设请求完成。
- ✅ 等待按钮恢复、错误提示出现或列表更新。
- ✅ 防抖使用 fake timer 精确推进，并在测试后恢复真实计时器。
- ✅ 先发 `old`、再发 `new`，让 `new` 先完成，最后完成 `old`；断言界面仍显示 `new`。
- ✅ abort 后断言没有失败 Toast、未处理 Promise 或错误日志。

### 案例：快照和覆盖率不能代替断言

**覆盖**：小范围快照、禁止大型快照、覆盖率风险视角、高风险针对性。

- ✅ 对稳定的错误码映射小对象使用可审阅快照。
- ❌ 对整页 2,000 行 DOM 快照点击“更新”来通过测试。
- ❌ 为提升行覆盖率调用函数却没有结果断言。
- ✅ 即使总体覆盖率很高，权限拒绝、迁移失败和重复提交仍各有针对性用例。

### 案例：测试与生产行为一起维护

**覆盖**：同步修改、修复不稳定根因、临时隔离条件、测试代码质量、删除失效内容。

- 行为合法变化时同步更新断言，并说明契约为什么改变；不能长期 `.skip`。
- 不稳定测试先查竞态、时间和共享状态。临时隔离必须记录原因、负责人或任务及恢复条件。
- 测试同样使用明确类型和职责命名，不能堆积 `any` 与万能 helper。
- 删除语言功能时同步删除失效资源 fixture 和测试，不保留永远无法运行的旧用例。
