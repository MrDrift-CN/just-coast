# Code Review 规范

## 适用范围

适用于 `web` 自有代码从准备修改到交付结果之间的持续审查，包括开发者自审、Codex 实施中审查、阶段性差异检查、自动修复后的复查和完成前验收。

本文件不负责 Pull Request 的批准、评审意见分级和合并决策；这些场景读取 `PReview.md`。

## 目标与分工

- Code Review 是开发活动的一部分，不是代码写完后的可选步骤。
- 审查目标是尽早发现需求偏差、错误边界、跨文件契约问题和无关改动，降低问题叠加后的返工成本。
- 自动化工具负责稳定、可机械判断的检查；人工语义审查负责行为、设计、风险和工具无法判断的边界。
- 自动检查全部通过不等于代码正确；人工审查不能重复争论 Prettier 已确定的格式。
- 开发中的审查对象是当前任务产生的完整变更，不限于已暂存文件。
- 审查不得扩大任务范围，不得擅自修复与当前目标无关的既有问题。

## 开发前审查

开始编辑前必须确认：

- 用户目标、验收行为和明确不做的内容。
- 受影响文件、调用方、公开入口、持久化结构和运行时边界。
- 当前工作树是否已有用户变更、未跟踪文件或与任务重叠的修改。
- 本 Skill 需要读取的领域规则，以及项目当前实际安装的依赖和生效配置。
- 上游或生成目录边界，避免把自有规范批量施加到官方源码。
- 最小可验证方案及相应的格式、lint、类型、测试、构建或人工验证范围。

不能只根据文件名或需求描述直接修改；必须阅读相关实现和调用链，确认假设与代码事实一致。

## 实施中的审查循环

每完成一个可独立理解的实现单元，必须进行一次小范围审查：

1. 查看该单元涉及文件的实际差异，而不是只回忆刚才写了什么。
2. 确认变化仍服务当前目标，没有顺带重构、格式化或重命名无关代码。
3. 检查调用方、导出、类型、资源、翻译和配置是否需要同步。
4. 运行成本合理的定向检查；自动修复后重新查看差异。
5. 先解决本阶段发现的阻塞问题，再继续叠加下一阶段代码。

以下情况必须立即进行阶段性审查，不能等到最后：

- 修改公共类型、组件 Props、Hook 返回值或模块导出。
- 修改状态所有权、持久化键、API DTO 或错误结构。
- 修改 Effect、订阅、计时器、请求取消或并发行为。
- 修改主题令牌、国际化资源、路由或构建配置。
- 直接修改上游或生成组件。
- 自动格式化、代码生成或迁移命令改动了多个文件。

## 语义审查清单

开发过程中根据变更范围检查以下内容；不适用的项目可以跳过，但不得跳过实际受影响的领域：

- **需求**：正常路径、空状态、错误状态、禁用状态和恢复路径是否符合预期。
- **范围**：是否存在当前需求之外的抽象、依赖、文件移动或行为变化。
- **类型**：是否准确表达契约，是否用 `any`、双重断言、非空断言或抑制指令隐藏问题。
- **边界数据**：URL、存储、API 和第三方输入是否经过运行时校验和领域转换。
- **状态**：是否保持单一事实来源，派生值是否被错误存储，更新是否不可变且原子。
- **异步**：是否处理取消、超时、过期结果、重复提交、清理和失败恢复。
- **React**：渲染是否纯净，Effect 是否确有外部同步职责，key 和依赖是否稳定。
- **UI**：语义 HTML、键盘、焦点、可访问名称、响应式和完整状态是否可靠。
- **主题与国际化**：是否使用语义令牌，用户文案、ARIA、日期和数字是否本地化。
- **安全与隐私**：权限、敏感数据、日志、URL、富文本、文件和凭据边界是否安全。
- **性能**：是否引入请求瀑布、过大依赖、重复全局监听或未经测量的复杂缓存。
- **维护性**：命名、职责、依赖方向、注释、文档和测试是否与行为同步。

## 自动审查层级

按变更风险使用项目实际可运行的检查：

1. **格式检查**：Prettier 处理格式和 Tailwind 类名排序。
2. **静态语义检查**：ESLint 检查 JavaScript、TypeScript、React Hooks 和项目边界。
3. **类型检查**：TypeScript 验证跨文件契约和严格类型。
4. **CSS 检查**：CSS 变化运行 `npm run lint:css`；Stylelint 警告必须确认属于已记录的受控例外。
5. **行为测试**：运行已有的相关单元、组件、集成或端到端测试。
6. **生产验证**：路由、构建、环境、懒加载或生产行为变化时运行构建。
7. **人工验证**：UI 和浏览器行为按受影响场景验证，不能由静态工具替代。

检查应从变更文件和受影响模块开始，再根据风险扩大到全项目。提交前工具只检查暂存文件，不足以覆盖开发过程中尚未暂存和未跟踪的变更。

## 差异与范围审查

- 审查前先查看工作树状态，区分用户既有改动、当前任务改动和生成结果。
- 必须检查未暂存、已暂存和未跟踪文件，不能只看一种 Git 状态。
- 查看文件差异、变更统计和必要的完整文件上下文；单独查看 diff 可能遗漏新文件和调用链。
- 自动修复、格式化和生成命令执行后必须重新审查差异，防止工具扩大范围。
- 禁止通过暂存文件隐藏尚未完成或有问题的当前任务变更。
- 禁止修改、覆盖或回退无法确认归属的用户变更。
- 发现无关既有问题时记录并报告；只有它阻塞当前目标且得到任务范围授权时才修改。

## 失败与冲突处理

- 检查失败时先判断是否由当前变更引起，并保存能够定位问题的证据。
- 当前变更造成的失败必须修复，不能通过关闭规则、扩大 ignore、添加不安全断言或跳过命令处理。
- 与当前变更无关的既有失败不得伪装成本次成功，也不得在未经授权时顺手扩大修复范围。
- 规则、配置、代码事实和用户要求冲突时停止扩散修改，按 Skill 的优先级完成裁决并记录结果。
- 无法安全验证的高风险行为必须明确报告限制，不能用“应该可以”代替证据。

## 完成前自审

交付前必须重新审查完整变更集，而不是直接复用开发中的局部结论：

- 对照用户目标逐项确认已完成、未完成和明确排除的内容。
- 检查所有改动文件、新文件、删除和重命名是否必要且归属正确。
- 确认代码、类型、资源、配置、文档和测试形成一致的完整变更。
- 运行与风险匹配的最终检查，并记录实际执行结果。
- 确认不存在调试代码、临时文件、敏感信息、无依据的规则抑制和无关格式变化。
- 对 UI 变更检查相关视口、主题、语言、焦点、状态和控制台。
- 明确剩余风险、未运行检查、既有失败和需要用户决定的事项。

最终交付说明至少包含结果、关键文件、验证、风险或限制。不能只说“已完成”。

## 项目案例

以下案例覆盖开发前、实施中、自动化、语义、差异、失败和完成前审查。案例中的命令只在项目实际存在对应能力时运行。

### 案例：动手前先识别既有改动

**覆盖**：用户目标、调用链、工作树、规则、依赖、上游边界和验证方案。

- ❌ 看到“修改登录页”就直接覆盖 `src/auth/pages/login.tsx`，没有确认该文件已有用户改动和新建表单组件。
- ✅ 先查看工作树和认证模块调用链，区分已有变更；读取 React、组件、Hooks、API、安全、i18n 和开发审查规则，再确定只修改必要文件及验证范围。
- ✅ 如果目标涉及 `components/ui`，先确认能否通过自有包装完成，不能先批量修改官方组件。

### 案例：公共契约修改后立即审查

**覆盖**：阶段性差异、调用方同步、阻塞问题先处理和必须即时审查的高风险变化。

修改 `useLogin()` 返回值后：

1. 立即查看 Hook 和调用方差异。
2. 搜索所有 `useLogin` 使用位置，更新公开类型和解构字段。
3. 检查 loading、error、取消和重复提交语义。
4. 运行相关格式、lint 和 typecheck。
5. 自动修复后重新看 diff，确认没有改动无关页面，再继续下一阶段。

### 案例：工具通过仍然存在语义错误

**覆盖**：自动化与人工分工，以及完整语义清单。

```tsx
const [fullName, setFullName] = useState("");

useEffect(() => {
  setFullName(`${firstName} ${lastName}`);
}, [firstName, lastName]);
```

这段代码可能通过格式、lint 和类型检查，但开发审查仍应发现：`fullName` 是派生值，不应使用 State 和 Effect 复制；额外渲染和同步风险属于语义问题。

### 案例：检查完整工作树而非只看暂存区

**覆盖**：未暂存、已暂存、未跟踪文件，差异上下文、自动修复复查和用户改动保护。

- ❌ 只运行 `git diff --cached`，遗漏尚未暂存的 API 修改和未跟踪翻译资源，然后宣称变更完整。
- ✅ 同时检查工作树状态、已暂存与未暂存差异，并打开未跟踪新文件确认内容和调用关系。
- ✅ Prettier 或代码生成运行后再次查看统计和文件差异；发现无关用户文件时保持不动并在交付中说明。

### 案例：按风险组合自动审查

**覆盖**：格式、ESLint、类型、Stylelint 条件、测试、构建和人工验证。

认证表单行为变化的检查组合：

```text
变更文件 Prettier
npm run lint
npm run typecheck
相关测试（项目存在时）
npm run build
人工验证：重复提交、错误恢复、键盘、两种语言、亮暗主题
```

当前项目已接入 Stylelint、Commitlint、lint-staged 和 Husky，但只有实际执行相应命令或 Hook 才能报告通过；自动化测试仍未接入，应按 `tooling.md` 如实说明。

### 案例：正确处理既有失败

**覆盖**：失败归属、禁止降级规则、既有问题边界、冲突裁决和证据。

- 当前修改引入类型错误：必须修复，不能加 `as unknown as` 或扩大 `exclude`。
- lint 在未触及的旧文件失败：确认基线和归属，保留失败输出；如果不阻塞当前工作则报告，不擅自重构该模块。
- 安全规则与实现需求冲突：停止继续扩散，说明冲突和安全后果，完成明确裁决后再实施。

### 案例：交付前重新审查完整变更

**覆盖**：目标回看、文件完整性、跨资源一致、最终检查、临时内容、UI 矩阵和交付说明。

```text
结果：修复语言旧键迁移，不丢失有效偏好。
文件：locale 解析、存储适配器、双语言资源、迁移测试。
验证：格式、lint、typecheck、测试和生产构建通过；手动验证刷新与跨标签同步。
风险：存储不可用时回退默认语言；没有修改用户现有其他工作树内容。
```

如果某项检查没有运行或项目尚无相应工具，明确写出原因；不能把“未执行”表述成“通过”。
