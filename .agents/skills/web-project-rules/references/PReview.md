# PReview 规范

## 适用范围

适用于 Pull Request、合并前变更集、他人提交和批准决策的审查，重点是判断一个完整变更是否可以安全合并。

开发过程中的持续自审、阶段性差异检查和完成前验收使用 `codeReview.md`。

## 目标

代码评审的首要目标是确保变更在正确性、安全性、可维护性和用户价值上改善项目整体健康度。评审不追求不存在的“完美代码”，但不得接受明确降低代码质量或扩大风险的变更。

## 作者责任

提交评审前，作者必须：

- 保证变更聚焦于一个清晰目标。
- 自己完整检查差异，删除调试代码和无关修改。
- 运行与变更相关的格式、lint、类型、测试和构建检查。
- 在描述中说明目的、关键取舍、验证结果、风险和迁移步骤。
- 对 UI 变化提供足够的视觉证据。
- 标明上游组件、生成代码、依赖、配置和持久化结构的变化。
- 将需要评审者特别关注的安全、并发、国际化、可访问性问题主动指出。

评审说明不能只写“已完成”或“修复问题”，必须让不了解实现过程的评审者理解变更为什么存在。

## 变更规模

- 一个 PR 应是一个可独立理解、验证、合并和回退的变更。
- 不以固定行数机械判断大小；如果评审者无法在合理时间内理解设计和风险，就应拆分。
- 大功能按稳定接口、基础重构、功能实现和后续清理等自洽阶段拆分。
- 重构和行为变更原则上分开提交。
- 测试与对应行为变更放在同一 PR，除非先补测试是后续安全重构的前置步骤。
- 每个阶段合并后项目必须保持可构建和可运行。

## 评审优先级

评审按以下顺序进行：

1. 需求和用户行为是否正确。
2. 安全、隐私、数据完整性和权限边界。
3. 整体设计、职责划分和依赖方向。
4. 状态、异步、错误和并发边界。
5. 国际化、主题、可访问性和响应式表现。
6. 测试是否能有效发现回归。
7. 性能和资源成本。
8. 命名、注释、文档和局部可读性。
9. 已由工具负责的格式细节。

不能用纯风格偏好阻塞一个符合项目规范的变更。

## 必查内容

评审者必须检查：

- 设计是否比实际需求更复杂，是否出现提前抽象或猜测性功能。
- 每个自有代码变更是否能够解释，不能跳过难以理解的代码块。
- 类型是否准确，是否通过断言、宽泛类型或忽略规则隐藏问题。
- Effect、订阅、请求和计时器是否正确清理。
- 旧响应、重复提交和错误恢复是否可靠。
- 用户可见文案是否国际化，日期和数字格式是否正确。
- 主题是否使用语义令牌，亮暗模式和焦点状态是否完整。
- 交互是否支持键盘和辅助技术。
- 是否引入敏感数据泄漏、XSS、不安全 URL 或权限绕过。
- 测试是否验证行为并能在实现错误时失败。
- 文档和配置是否随行为变化同步更新。

## UI 评审

UI 变更除代码外还要检查：

- 常用视口和窄屏布局。
- 亮色、暗色和系统主题。
- 中文、英文和较长文案。
- 键盘导航、焦点顺序和焦点可见性。
- 加载、空、错误、禁用和成功状态。
- reduced-motion 设置。
- 浏览器控制台错误和明显的布局抖动。

## 上游和生成代码

- 上游或生成文件不要求逐行应用自有风格，但必须确认差异来源和必要性。
- 评审应重点检查本地定制是否最小、是否能在更新时保留、是否可以改用包装或主题能力。
- 禁止接受无法说明来源的大规模覆盖。
- 如果生成文件被深度改造，应要求明确其后续所有权。

## 评审意见

评审意见应针对代码和影响，不针对开发者本人，并尽量说明原因。

统一使用以下级别：

- **阻塞**：正确性、安全、数据、规范或明显维护风险，合并前必须解决。
- **建议**：存在更合理实现，但当前实现不构成阻塞风险。
- **细节**：小范围可读性或一致性优化，可由作者判断是否处理。
- **问题**：需要补充上下文，尚未形成修改结论。

作者不同意阻塞意见时，应提供代码事实、测试、性能数据或明确设计依据。无法通过事实达成一致时，记录最终裁决，避免同一问题反复争论。

## 通过标准

可以批准一个仍有非阻塞改进空间、但整体明确提高代码健康度的变更。不得因为个人理想方案无限拖延，也不得以赶进度为由合并已知会降低正确性、安全性或可维护性的代码。

## 项目案例

以下案例覆盖本文件全部规则章节。评审案例使用“事实、影响、建议”表达，不把个人偏好包装成项目要求。

### 案例：作者提交前自检

**覆盖**：聚焦、自查、验证、描述、视觉证据、特殊文件标记和高风险提醒。

一个合格的评审说明示例：

```text
目的：防止快速切换搜索词时旧响应覆盖新结果。
关键取舍：请求替换时 Abort 前一个请求，并以请求 ID 二次保护。
验证：格式、lint、typecheck、竞态测试；Chrome 慢速网络人工验证。
风险：AbortError 不应显示错误 Toast。
特别关注：Effect 清理和过期结果分支。
```

UI 变化再附亮/暗、窄屏和长文案证据；修改上游、依赖、配置或存储结构必须点名。只写“完成”或“修复问题”不能进入评审。

### 案例：按可理解性拆分变更

**覆盖**：单一可回退目标、不用机械行数、稳定阶段、重构/行为边界、测试同 PR、每阶段可运行。

- ❌ 一个 PR 同时搬迁 `auth` 目录、引入测试框架、重写登录、替换主题和全仓格式化。
- ✅ PR 1 独立引入测试能力并提供示例；PR 2 用测试锁定旧行为并重构请求适配器；PR 3 实现登录修复和对应测试。
- 边界：功能所需的两行局部清理可以同 PR；不能为了“纯粹”拆成一个中间无法构建的提交。

### 案例：评审顺序先风险后样式

**覆盖**：需求、安全、设计、状态并发、i18n/主题/a11y/响应式、测试、性能、可读性、工具格式。

看到一个登录按钮差异时，正确顺序是：

1. 确认点击是否提交正确请求、是否能重复提交。
2. 确认令牌、权限和错误消息没有泄漏。
3. 检查请求、Hook、组件职责与取消边界。
4. 检查文案、焦点、亮暗主题和窄屏。
5. 检查回归测试和包体积影响。
6. 最后检查命名和注释；Prettier 已决定的空格不作为人工阻塞意见。

### 案例：从真实差异发现问题

**覆盖**：复杂度、全部自有改动、类型绕过、清理、竞态、i18n、主题、a11y、安全、测试和文档。

假设差异同时出现：

```tsx
const response = data as unknown as User;
useEffect(() => window.addEventListener("storage", sync), []);
return (
  <div onClick={save} className="bg-red-500">
    Save
  </div>
);
```

评审必须指出：

- DTO 未做运行时校验且用双重断言隐藏问题。
- 监听器没有对称清理，依赖也可能不完整。
- 可点击 `div` 无键盘语义，`Save` 未国际化。
- 原始色板绕过主题，状态只靠颜色表达。
- `save` 是否防重复、失败能否恢复以及测试是否能复现错误均需确认。
- 若行为或配置改变，相关文档必须同步。

### 案例：UI 评审矩阵

**覆盖**：视口、主题、语言、键盘、状态、reduced-motion、控制台和布局稳定。

| 维度 | 至少检查                                 |
| ---- | ---------------------------------------- |
| 布局 | 常用宽屏、窄屏、文本放大                 |
| 主题 | 亮色、暗色、system 跟随                  |
| 文案 | `zh-CN`、`en-US`、人为长文案             |
| 交互 | Tab 顺序、Enter/Space、Escape、焦点返回  |
| 状态 | loading、empty、error、disabled、success |
| 动画 | reduced-motion 后仍能理解状态            |
| 运行 | 控制台无新错误，异步内容无明显跳动       |

只看一张默认主题桌面截图不足以批准交互 UI。

### 案例：评审上游和生成代码

**覆盖**：不强求自有风格、差异必要性、最小定制、拒绝来源不明覆盖、明确所有权。

- ✅ 官方更新产生大量可追溯差异时，不逐行要求改为自有 kebab-case；重点检查版本来源、产品回归和本地 patch 是否保留。
- ❌ 接受无法说明命令、版本和原因的整目录覆盖。
- ✅ 能用主题变量或自有包装解决时撤销上游修改；深度定制无法升级时要求迁出并声明为自有组件。

### 案例：四级评审意见

**覆盖**：针对代码、说明原因、阻塞/建议/细节/问题，以及分歧用事实裁决。

```text
[阻塞] 旧请求可以覆盖当前搜索结果，会向用户展示错误账户；请取消前一请求或验证请求标识，并补竞态测试。
[建议] 这段映射已经在两个模块共享稳定语义，可以考虑提取到 authAdapter。
[细节] accountData 可命名为 accountSummary，职责更明确；不影响合并。
[问题] 这里保留旧存储键的发布周期是什么？当前差异里没有移除条件。
```

不要写“你这代码很差”。作者不同意阻塞意见时，用测试、运行时事实、性能数据或规则边界回应；最终裁决被记录后不重复争论。

### 案例：批准标准

**覆盖**：允许非阻塞空间、禁止理想化拖延、禁止以进度接受已知风险。

- 可以批准：命名仍有一个“建议”级改进，但变更正确、安全、有测试且整体提升健康度。
- 不可批准：已知会丢失用户设置、绕过权限或产生竞态，只因发布日期接近而接受。
- 不应拖延：评审者偏好另一种同样合规的组件拆分，却无法证明当前方案有实际风险。
